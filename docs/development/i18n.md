## Current architecture

PastExamWeb uses Vue and `vue-i18n`. Locale messages live in
`frontend/src/i18n/messages.js`; the current catalog primarily uses Traditional
Chinese source-language literals as keys, with a small number of established
semantic keys whose Traditional Chinese values are explicit overrides.

Use the existing translation entry points for their current contexts:

- `$t(...)` in Vue templates and Options API code;
- `t(...)` from `useI18n()` in Composition API code;
- `i18n.global.t(...)` outside components; and
- `getMessageTemplate(...)` where a component needs the uninterpolated template
  for an existing integration.

Do not introduce a second catalog or translation architecture for ordinary
copy changes.

## Translation completeness

Every statically used localized key must have an explicit own-property mapping
in the English catalog. Falling back to the source key is not English coverage.
For example, `$t('審核狀態')` requires an entry such as
`審核狀態: 'Status'` in the English catalog.

This applies to localized user-visible text across table headers, buttons,
headings, placeholders, filters, dialogs, tooltips, status labels, empty,
error, and recovery copy, `aria-label`, `title`, and duplicated mobile or
responsive copy. It does not require every arbitrary application string
literal to use i18n.

Before translating an existing concept, search the catalog and nearby UI and
reuse established English terminology when appropriate. Do not rewrite
unrelated translations opportunistically.

## Interpolation placeholders

The set of interpolation placeholder names in the source message and English
translation must match. Order may differ. For example:

- Source: `{label}：{count} 位活躍使用者`
- English: `{count} active users in {label}`

Both contain `label` and `count`, so they match. An English value of
`{count} active users` is invalid because it loses `label`; extra or renamed
placeholders are invalid for the same reason.

Callers must also supply every required interpolation argument. The rendered
UI must not expose unresolved literal placeholders such as `{label}` or
`{count}`.

## Static and dynamic keys

The repository has legitimate dynamic translation keys, including cataloged
option labels, status mappings, SEO metadata, and server-provided error text.
The initial automated guard deliberately checks only literal keys written
directly in established calls such as `$t('...')`, `t('...')`,
`i18n.global.t('...')`, and `getMessageTemplate('...')`. Review dynamic-key
behavior with focused reasoning and tests; do not force arbitrary dynamic
expressions into this lightweight static check.

## Verification

Run `pnpm i18n:check` from `frontend/` for i18n and copy changes. The checker
enforces explicit English mappings for static literal usages and placeholder
set parity across catalog messages.

Existing debt is recorded by exact rule, key, and applicable placeholder-set
identity in `frontend/scripts/i18n-baseline.json`. A matching known violation is
allowed; an unbaselined violation and a stale entry for a fixed violation both
fail.
Never add new debt to the baseline. Fix an existing violation and remove its
entry in the same change, so the baseline can only shrink.

The initial cleanup inventory contains six missing English keys (`載入更多`,
`儲存失敗`, `來源已不存在`, `許願送出失敗`, `輸入課程中文名稱`, and `轉移失敗`)
and eight placeholder mismatches (`公開課程 SEO 有資料`, `公開課程 SEO 無資料`,
`課程公開考古題中繼資料`, `公開課程 SEO 標題`, `投稿等級最高`, `投稿等級進度`,
`投稿統計項目`, and `投稿統計摘要`). Resolve that inventory in a separate
translation-cleanup PR.

For ordinary i18n or copy-only changes, verification normally consists of the
i18n contract checker, a focused frontend unit test when runtime rendering or
interpolation changed, and focused lint or static checks. Follow the
[validation policy](validation.md); backend or database tests, Docker,
production builds, Playwright, and multi-browser E2E are not required unless
the actual change independently justifies them.
